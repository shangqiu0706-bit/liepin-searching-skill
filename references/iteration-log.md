# Skill 迭代登记

本文件只记录用户明确标记为 `迭代：`、并且具有跨案例复用价值的规则；当前案例的公司、人选、薪资和一次性查询写入案例目录，不写入这里。

最新的岗位自适应规则优先于早期案例中的具体行业、公司类型和工具示例。早期条目保留为历史经验，不能直接当作新岗位的默认搜索词或公司清单。

## 2026-08-31

- 搜索行业不要过早收窄到单一品类：当 JD 涉及母婴/儿童或内容电商时，同时看儿童教育、童书、玩具、儿童营养、婴童用品及可迁移的成人快消内容岗位。
- 发现候选人的公司要进入公司反查队列；公司内部的内容、电商、直播、用户增长、品牌、品类和运营岗位可能比关键词搜索更容易找到合适人选。
- 内容-first 候选人要单独搜索 `千川`、`云图`、`种草`、`投流`、`素材`、`内容策略` 等工具/方法词，不要求简历出现“品类负责人”字样。
- 甲方、乙方/DP/MCN、平台服务商都可进入发现池；最后仍按用户给出的年龄、城市、薪资等硬条件分为严格池和边界池。

## 2026-08-31

- 迭代来源：用户消息中的“迭代：要根据不同的岗位去进行公司的搜寻……关键词要根据岗位的不同去改变”。
- 新规则：公司搜索轴、平台/工具/方法关键词和行业/场景范围必须从当前岗位 JD 重新推导；不得把上一岗位的公司或关键词设为默认，只有相同或高度相似工作内容并完成相似性判断后才可复用具体搜索资产。
- 影响：搜索矩阵、公司反查和跨案例记忆复用。
- 理由：不同岗位的业务对象、职责和候选人表达方式不同；可跨岗位复用的是“通过对的候选人发现公司，再按当前岗位等价职能反查”的方法逻辑。
- 操作补充：当 JD 无法提供足够区分度时，可先做基础搜索并询问用户是否有参考关键词/公司；用户补充默认只服务当前案例。

## 2026-09-08

- 迭代来源：用户复盘候选人 searching，明确薪酬范围只要与岗位范围有交集即可保留；公司和职位名称匹配、但未展示具体工作内容的人也应保留为待验证线索。
- 新规则：默认不以搜索页薪资筛选卡死召回；以详情页期望薪资为事实源，按相同月薪口径判断区间交集。存在实际交集即保留，只有一个端点相接标为薪资卡线/待确认，完全无交集才视为不匹配。公司、职位和行业信号可用于发现和进入待验证池，但不能代替业务证据进入已验证 shortlist。
- 影响：搜索矩阵 / 详情页核验 / 薪资判定 / 候选人分层 / 交付。
- 理由：搜索页的薪资展示与薪次数信息不完整，且过窄筛选会漏掉可谈候选人；公司与职位是有价值的结构性信号，但未披露工作内容时应诚实标注证据缺口。
